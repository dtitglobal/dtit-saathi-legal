# Saathi 1.4.1 — disclosure drafts

**DRAFT for Rajat's approval. Nothing here is filed, published or merged.**

What 1.4.1 adds: PostHog product analytics (US cloud, `us.i.posthog.com`) and
Linkrunner install attribution (link domain `go.dtitglobal.com`), both running for
everyone from app launch including guests, except App Review and internal test
accounts. Coin revenue reaches Linkrunner via a RevenueCat webhook (server to
server). No session replay, no autocapture, no PostHog logs, no Meta SDK, no
uninstall tracking, no server push.

## 2. Google Play — Data safety delta

Baseline: what was filed 19 Nov 2026 for 1.4.0 (`docs/1.4.0/release-runbook.md`
§8.6 in saathi-main): Purchase history; Approximate location shared; App
interactions; Diagnostics shared; Device or other IDs shared; Ads = Yes;
Advertising ID = Yes.

1.4.0 already declares the hard categories, because AdMob needed them. The 1.4.1
delta is mostly **adding purposes and recipients to rows that already exist**.

| Data type | 1.4.0 answer | 1.4.1 change | Collected | Shared | Purposes | Required? | Ephemeral? |
|---|---|---|---|---|---|---|---|
| **Device or other IDs** | Collected + shared (AdMob advertising ID) | **Change:** add Linkrunner as a recipient and **Analytics** as a purpose. Linkrunner reads the advertising ID, Android ID, App Set ID and Google Play install referrer, and passes identifiers on to the ad network | Yes | Yes | Advertising or marketing; **Analytics** (new) | Required | No |
| **App interactions** | Collected, not shared | **Change:** now also **shared** — the named events go to PostHog, and four of them to Linkrunner. Add **Analytics** purpose | Yes | **Yes** (new) | Analytics; App functionality | Required | No |
| **Approximate location** | Collected + shared (AdMob, from IP) | **Change:** add PostHog and Linkrunner as recipients. Both derive approximate location from the IP their servers see; Linkrunner's own docs answer this row "Yes, worked out from the IP address" | Yes | Yes | Advertising or marketing; **Analytics** (new) | Required | No |
| **Diagnostics** | Collected + shared (Sentry, AdMob) | **No change.** PostHog error-tracking autocapture is off and PostHog logs are off | Yes | Yes | unchanged | unchanged | unchanged |
| **Purchase history** | Collected (RevenueCat), app functionality | **Change:** now also **shared** — the RevenueCat webhook tells Linkrunner a coin purchase happened. Add **Analytics** purpose. No price or transaction id is sent from the app; confirm what the webhook carries (open question 5) | Yes | **Yes** (new) | App functionality; **Analytics** (new) | Required | No |

Rows that need **no** change: Name, Email address, Phone number, Photos, Audio,
Files, Health, Financial info, Messages, Contacts, Calendar, Web browsing. None
of them reaches PostHog or Linkrunner — the event property whitelist in
`apps/mobile/lib/analytics/events.ts` makes that structural, not a convention.

Play's taxonomy has no dedicated "attribution" type, and **App interactions** is
the right home for it, so the recommendation is to widen that row rather than add
an "Other actions" row.

Other Data safety answers:

- **Data is encrypted in transit:** stays Yes. Both SDKs use HTTPS.
- **Users can request data deletion:** stays Yes. Deleting the account removes
  the records held under the Saathi account ID; policy §2.14 now says so and
  gives the email route.
- **Independent security review:** unchanged.
- **Ads / Contains ads:** stays Yes.
- **Advertising ID = Yes:** already Yes. Still needs the App bundle explorer
  check that the prod bundle has `com.google.android.gms.permission.AD_ID`
  (runbook §8.6 already requires this). For 1.4.1 that permission arrives from
  two libraries rather than one — AdMob, and Linkrunner's
  `play-services-ads-identifier` dependency — so the check should still pass.

One thing to watch: Linkrunner's Android SDK declares `<queries>` entries for
Facebook, Instagram and Facebook Lite so it can read Meta's install referrer.
That is a manifest `<queries>` block, not the `QUERY_ALL_PACKAGES` permission,
and Linkrunner's docs state the SDK "does not read ... the list of installed
apps". It therefore needs no Data safety row, but it will appear in the merged
manifest and is worth knowing before anyone is surprised by it.

### The SKAN / no-IDFA reasoning — flag this for Rajat

The part most likely to draw a reviewer question, so worth being precise:

1. **Linkrunner never touches the IDFA on iPhone.** The app initialises it with
   `disableIdfa: true` (`apps/mobile/lib/analytics/analyticsNative.ts`, and the
   `expo-linkrunner` plugin option in `app.json`). Linkrunner's docs are explicit
   that this turns off both IDFA collection and the SDK's own ATT prompt. The
   adapter also never calls the SDK's `requestTrackingAuthorization` method —
   verified by grep across the mobile app.
2. **The only ATT prompt in Saathi stays where it is**, on the first "Watch
   video" tap, with its current `expo-tracking-transparency` text. It is asked
   for AdMob, not for analytics or attribution. Because `disableIdfa: true` is
   set, the Linkrunner plugin does **not** write its own
   `NSUserTrackingUsageDescription`; the one in the Info.plist is ours.
3. **Linkrunner attributes via SKAdNetwork instead.** The plugin writes
   `NSAdvertisingAttributionReportEndpoint` and `AttributionCopyEndpoint` =
   `https://linkrunner-skan.com` into the Info.plist, so Apple sends a copy of
   the SKAN postback to Linkrunner. This is new to the 1.4.1 Info.plist and
   earns a line in the review notes (§4).
4. **So why is "Used for tracking" still Yes?** Because of AdMob, not
   Linkrunner. Saathi already answers Yes for 1.4.0 (IDFA with ATT for the
   reward videos). 1.4.1 does not change that answer.
5. **Does the IDFV make Device ID "used for tracking"?** Apple's definition of
   tracking is linking data with third-party data for targeted advertising or ad
   measurement, or sharing it with a data broker. Linkrunner does share
   attribution data — including the IDFV and the approximate location derived
   from the IP address — with the ad network that showed the ad, which is ad
   measurement with a third party. Since the app already answers Yes to the
   tracking question, declaring **Device ID as linked + used for tracking**
   (which 1.4.0 already does for the IDFA) covers the IDFV too, and is the
   conservative answer. **Recommendation: keep tracking = Yes and leave Device
   ID marked as used for tracking.** The alternative — arguing the IDFV is
   vendor-scoped and therefore not tracking — is defensible but gains nothing,
   because the AdMob answer already puts the app in the tracking bucket.

## 5. Open questions for Rajat

1. **PostHog "Discard client IP data" — on or off?**
   The setting is **Settings → Project → IP data capture configuration → Discard
   client IP data**. Two things to know first:
   - Turning it on stops the `$ip` property being **stored**, but PostHog's
     servers still **receive** the IP, and the GeoIP enrichment transformation
     still adds `$geoip_country_name`, `$geoip_city_name` and friends to events
     and persons. To stop location enrichment as well, the GeoIP transformation
     has to be disabled separately in the project's transformations.
   - Draft §2.14 says an approximate location "can be worked out" from the IP,
     which is true either way. If both the IP discard **and** the GeoIP
     transformation are turned off, that sentence can be narrowed for PostHog and
     the Play "Approximate location" recipient list shortened to AdMob and
     Linkrunner. **Recommendation: turn both off for PostHog** — Saathi's events
     already carry an app language, country-level geography adds little, and it
     simplifies three disclosures at once. Linkrunner's IP-derived location
     cannot be turned off, so that row stays either way.
2. **An in-app analytics opt-out — yes or no?**
   There is none today: `lib/analytics/gate.ts` has no user-facing switch, only
   the build keys and the server's `analyticsExcluded` flag. India's DPDP Act is
   consent-based, and the policy's §8 rights list currently offers withdrawal of
   consent for AI processing but not for analytics. Options:
   - **(a)** No toggle. Rely on the consent screen line, the policy, and the
     email route for deletion. Simplest; what the draft assumes.
   - **(b)** A Settings toggle that writes to the existing gate. The plumbing is
     already there — PostHog has `optOut()`, and the gate already supports a
     "don't measure" state — so this is a small app change, not a redesign.
   - **Recommendation: (b), but not as a 1.4.1 blocker.** It is the cleanest
     answer to a DPDP question and to a store reviewer, and the gate was built in
     a way that makes it cheap. If it ships later, §8 of the policy gains the
     line then, not now.
3. **Retention — what goes in §7?**
   The policy currently carries `[PLACEHOLDER — confirm with Rajat]`. PostHog
   Cloud retention is plan-dependent: 1 year on Free, 2 years on Pay-as-you-go,
   up to 3 on Boost, and expired events are cleaned up monthly, so an event can
   linger about two months past the period. **Which PostHog plan is the Saathi
   project on?** Linkrunner publishes no retention period at all (see Part 1), so
   either we ask them and quote the answer, or §7 says their period is set by
   their own policy without naming a number.
4. **Should the consent screen name PostHog and Linkrunner?**
   The draft options do not — they say "we measure how the app is used and which
   of our own ads and links bring people to Saathi", and the policy names both
   providers. The AI sentence immediately before it *does* name Anthropic, Cohere
   and Groq, so there is an argument for symmetry. **Recommendation: don't name
   them.** Users recognise Anthropic as the thing answering their question;
   PostHog and Linkrunner are plumbing, and naming them makes a screen people
   must read through longer without telling them anything they can act on.
5. **What exactly does the RevenueCat → Linkrunner webhook send?**
   The app deliberately sends no price and no transaction id (see the comment on
   `linkrunnerEventFor` in `events.ts`). But the webhook is configured in the
   RevenueCat and Linkrunner dashboards, not in our code, so what it carries is
   not visible from the repo. If it forwards the **price and currency**, that is
   fine for the policy as drafted (§2.14 says RevenueCat tells Linkrunner a
   purchase happened), but it means Play's Purchase history row is shared with a
   second recipient and should say so. **Worth one look at the webhook payload in
   the Linkrunner dashboard before filing Data safety.**
6. **Does the `go.dtitglobal.com` link domain need its own mention?**
   The policy does not name it. It is our own subdomain pointed at Linkrunner's
   link service, so anyone tapping a Saathi campaign link hits Linkrunner's
   servers before the app opens — which means Linkrunner sees the click (IP, user
   agent, referrer) even for people who never install. §2.14 covers what happens
   after install. **Recommendation: add one sentence to §2.14 saying our campaign
   links go through Linkrunner before they reach the app or the store.** Not
   drafted yet, pending Rajat's view.
7. **Privacy mode is off, deliberately — confirm that is still the call.**
   Linkrunner has a `privacyMode` that would stop it reading the advertising ID,
   the Android ID, the carrier and the device IP, and on iPhone the IDFV. It is
   off, which is what makes Android attribution work. Worth confirming the trade
   is understood, because it is the single biggest driver of the Play "Device or
   other IDs" and "Approximate location" rows.
